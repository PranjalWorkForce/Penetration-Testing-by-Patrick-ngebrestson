# theHarvester — Full Methodology Note

## What it is
theHarvester (maintained at github.com/laramies/theHarvester) is a passive/semi-passive OSINT reconnaissance tool used in the early stages of a penetration test or red team engagement. It aggregates data from public sources to map a target's external footprint — emails, subdomains, hostnames, IPs, URLs, and employee names — without directly touching the target's infrastructure (for the passive modules).

## Installation
```bash
# Requires Python 3.12+
curl -LsSf https://astral.sh/uv/install.sh | sh
git clone https://github.com/laramies/theHarvester
cd theHarvester
uv sync
uv run theHarvester
```
Kali/Parrot ship it preinstalled. An optional REST API (`/additional/*` routes) can be protected with `THEHARVESTER_API_KEY`.

## Core syntax
```bash
theHarvester -d <domain> -b <source> [options]
```
Key flags:
- `-d` target domain
- `-b` source/module (or `all`)
- `-l` limit number of results
- `-S` start result offset (paging)
- `-f` output to file (`.json`/`.xml`/`.html`)
- `-c` DNS brute-force common subdomains
- `-n` DNS reverse lookup on discovered IP ranges
- `-t` DNS TLD expansion
- `-v` verify hosts via DNS resolution and search for virtual hosts
- `-e` use a custom DNS server
- `-r` use Shodan to query discovered hosts
- `-s` start screenshot capture of subdomains (requires additional setup)

## Data sources (modules)
Modules fall into two rough categories:

**No API key required (fully passive):**
baidu, bing, crtsh, certspotter, dnsdumpster, duckduckgo, hackertarget, rapiddns, otx (AlienVault), threatminer, urlscan (partial), anubis, brave, linkedin/linkedin_links (via Google), sitedossier

**API key required:**
bingapi, censys, github-code, hunter, intelx, fullhunt, binaryedge, bevigil, criminalip, tomba, shodan, securitytrails, and several others. Keys go in `api-keys.yaml`.

Run `theHarvester -d target.com -b all` to hit every source you have keys for; run selectively when you want to control noise or attribution (see OPSEC below).

## Methodology — how to actually use it in an engagement

**1. Scoping**
Confirm the domain(s) are in-scope before running anything, even passive lookups. Passive OSINT is usually low-risk, but some modules (crtsh, DNS brute force with `-c`, virtual host verification with `-v`) can generate logged traffic against the target's own infrastructure or third parties.

**2. Baseline passive sweep**
```bash
theHarvester -d target.com -b bing,duckduckgo,crtsh,certspotter,dnsdumpster,hackertarget,otx,threatminer -l 500 -f baseline
```
This gives a first-pass inventory: emails, subdomains, and hosts with zero direct interaction with target infra beyond certificate-transparency logs (which are third-party CAs, not the target).

**3. Certificate transparency deep dive**
crt.sh and CertSpotter are usually the highest-yield subdomain sources. Cross-reference results against `censys` (if keyed) for corroboration and to catch expired/rotated certs the CT logs might miss.

**4. Search engine / people enumeration**
`google`, `bing`, `linkedin`, `linkedin_links` pull employee names and email address patterns (e.g., `first.last@target.com`), which is valuable for later phishing-simulation or password-spray planning (with authorization).

**5. DNS expansion (semi-active)**
- `-c` brute-forces a common subdomain wordlist against the target's DNS — this *does* touch the target's nameservers.
- `-n` performs reverse DNS on any IP ranges found.
- `-t` does TLD expansion (checks target.com, target.net, target.org, etc.).
These steps move from purely passive to "semi-passive" — flag this transition in your engagement notes/timeline.

**6. Correlation with Shodan/Censys**
`-r` (Shodan) or the censys module maps discovered hosts to exposed services/ports/banners — this is where recon starts to shade into external attack-surface mapping. Still generally passive (querying third-party databases), but treat the resulting host list as your next scanning target list, not something to actively touch yet.

**7. Consolidate and de-duplicate**
Export with `-f` to JSON, then merge across runs — theHarvester doesn't dedupe across separate invocations automatically. Feed the subdomain list into a resolver (massdns, dnsx) to confirm liveness before moving into active scanning tools (nmap, httpx, etc.).

**8. Handoff**
Output becomes the seed list for:
- Subdomain takeover checks
- Active service enumeration (nmap/masscan)
- Email list → phishing simulation or credential-exposure checks (haveibeenpwned-style, only with authorization)
- Org-chart / social-engineering pretext building

## OPSEC and legal notes
- Only run against domains you're authorized to assess — even "passive" recon against out-of-scope targets can violate computer-misuse laws in many jurisdictions.
- Google/Bing scraping modules can trigger CAPTCHAs or rate-limit/block your IP; consider rotating or throttling (`-l` limits) for sustained engagements.
- `-c` (brute force) and `-v` (virtual host verification) generate real DNS/HTTP traffic against the target — document this in your ROE (rules of engagement) and timeline.
- API-keyed modules (Shodan, Censys, etc.) associate queries with your account — be mindful of what that reveals about your engagement to the third-party provider.

## Limitations
- Coverage depends entirely on what's publicly indexed — internal assets, unlisted subdomains without certs, and non-indexed pages won't surface.
- Search-engine modules are fragile against UI/API changes and anti-scraping measures.
- No active vulnerability data — it's a footprinting tool, not a scanner. Pair it with tools like Amass, Subfinder, or Recon-ng for broader coverage, and nmap/httpx for the active phase that follows.
